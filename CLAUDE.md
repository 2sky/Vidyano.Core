## Architecture Overview

Vidyano.Core is a portable .NET client library for Vidyano backend applications following MVVM architecture:

### Core Components
- **Client.cs**: Central hub for backend communication and session management. Contains extensive internationalization support and handles all server interactions.
- **NotifyableBase.cs**: Foundation for property change notifications via INotifyPropertyChanged
- **ViewModelBase.cs**: Base class for view models, extending NotifyableBase with additional functionality
- **PersistentObject.cs**: Represents data entities with server synchronization capabilities
- **Query.cs**: Manages data queries and result sets from the backend

### Command System
Actions follow a hierarchical command pattern:
- **ActionBase.cs**: Abstract base for all actions
- **QueryAction.cs**: Query-specific operations
- Specialized actions in `ViewModel/Actions/` handle CRUD operations

### Key Architectural Patterns
1. **Observable Pattern**: All view models inherit from NotifyableBase for data binding
2. **Async-First Design**: Extensive use of async/await throughout Client operations
3. **Strong Typing**: Generic implementations for type safety (e.g., PersistentObject<T>)
4. **Immutable Collections**: Query results use immutable collections for thread safety

## Development Notes

### Demo Application
The solution includes a Demo console application that boots a **full Vidyano app in-process** (via the `Vidyano` package's Minimal API) on a Kestrel localhost port, then drives it with a `Vidyano.Core` client over real HTTP. It is fully self-contained — no `demo.vidyano.com`, no database, no config — so it runs offline. Use this to:
- Test library functionality (client + server in one process)
- Verify API changes work correctly
- Demonstrate usage patterns to developers (Minimal API model in `DemoModel.cs`, client flow in `Program.cs`)

The model is the same "shop" shape the `.visc` integration tests use (products in categories), minus their test-only hooks. To run the demo:
```bash
cd Demo
dotnet run
```

### No Test Project
This codebase currently lacks automated tests. When implementing new features:
- Ensure backward compatibility across all target frameworks
- Test manually against different .NET runtimes
- Consider impact on existing client applications
- Use the Demo app to verify basic functionality

### Internationalization
Client.cs contains translations for 30+ languages. When modifying error messages or user-facing strings, maintain consistency across all language dictionaries in the Client constructor.

### NuGet Package Generation
The project automatically generates NuGet packages on Release builds. Package metadata is defined in the .csproj file.

## Companion packages: Vidyano.Script + Vidyano.Script.Tool

The repository also ships two scripting packages built on top of Vidyano.Core. They live in this solution and ship from this repo.

### Vidyano.Script (library)
- Path: `Vidyano.Script/`
- Public façade: `Vidyano.Script.VidyanoScript` — `RunFileAsync(path, options)`, `RunAsync(body, options)`, `Lint(body)`.
- Engine layers: `Parsing/` (lexer + parser), `Diagnostics/` (errors + suggester), `Runtime/` (`VidyanoSession`, `Interpreter`, guards, `ScriptHooks`).
- `VidyanoSession` drives a real `Vidyano.Client` — there is no mocking. Whatever a `.visc` script does, a frontend could have done.
- `ScriptHooks` pins the session to `Environment="Web"` + `environmentVersion=3` so the server applies default filters and emits `IncludeFilters` exactly like a v4 browser session. It also forwards `Hooks.OnClientOperation` into the session's per-verb buffer (`_lastOperations`) and full-history buffer (`_allOperations`) — this is the pattern documented in PR #6's reply: hosts that want operation history record it in their `Hooks` subclass, not on `Client`.

### Vidyano.Script.Tool (CLI)
- Path: `Vidyano.Script.Tool/`
- Packs as a dotnet tool: `<PackAsTool>true</PackAsTool>`, command name `vidyano`.
- Subcommands: `run` (execute one file), `test` (run a suite), `lint` (parse-only), `repl` (interactive), `lsp` (language server over stdio), `help` (`help verbs` lists every `.visc` verb).
- Shared options: `--app`, `--var k=v`, `--mode navigation|audit|direct`, `--tools <path.dll>` (repeatable; loads `IVidyanoScriptToolPack` plugins), `--json` (NDJSON; now honored by `lint` too), `--verbose`, `--insecure` (dev TLS only).
- `run`/`test` add `--timeout <30s|2m|0>` (per-file; off by default). `test` adds positional files/dirs/globs, `--report junit|tap|sarif[:path]` (repeatable), and `--jobs <n>` (parallelism; serial by default). `test` rolls per-file outcomes into one exit code via the pure `SuiteExit.CodeFor`; `run` classifies its single file through the same `SuiteRunner.Classify`, so a no-base-URI script now exits `3` (was `2`).
- Suite engine lives in `Vidyano.Script/Runtime/`: `SuiteRunner` (per-file executor seam + bounded parallelism + per-file timeout), `SuiteResult`/`FileResult`/`FileOutcome`, pure `SuiteExit.CodeFor`, and `Reporting/` formatters (`IReportFormatter` + JUnit/TAP/SARIF — pure, deterministic, unit-tested in `Vidyano.Script.Tests`). Timing rides additively on `ScriptResult`/`StepResult.Duration` (observational; never in golden compares).
- Exit codes: `0` ok, `1` failed (incl. timeout), `2` parse error, `3` connection error, `64` usage (incl. no files discovered).

### `.visc` quick reference

> Mirrors `docs/visc-language.md` (the canonical reference). When a verb's grammar or semantics change, update this table, that doc, and `vidyano help verbs` (`Diagnostics/VerbCatalog.cs`) in the same change.

| Verb | Effect |
|---|---|
| `SIGN-IN <user> / <pwd>` | Authenticate (optionally `LANGUAGE xx-XX`). |
| `SIGN-IN FROM ENV` | Authenticate using `VIDYANO_USER` / `VIDYANO_PASSWORD` from the environment (loud-fails when either is unset). Optional `LANGUAGE xx-XX`. |
| `SIGN-IN @name = <user> / <pwd>` | Open a **named** session (the `=` is required). Mints its OWN cookie jar / identity, so it never shares auth with the default or any other named session. Re-`SIGN-IN @name` re-auths the existing slot in place (no nav-state reset). |
| `USE @name` | Switch the active session to a named one — all observable state (nav stack, current PO/Query, client operations, `@session`) swaps atomically. Only named sessions are addressable (the default `""` session is unreachable by name); an unknown name fails with `resolve-session` + a suggestion. |
| `SIGN-OUT` / `SIGN-OUT @name` | Faithful `viSignOut` (real server action + auth clear) against the current (bare) or named session. A named (minted) session is then disposed + removed; the default session is left present-but-disconnected. If the signed-out session was active, the active session falls back to the default slot. |
| `OPEN MenuItem <path>` | Push a Query frame on the nav stack. |
| `OPEN-ROW <i>` | Push a PO frame from row `i` of the top Query (by index). |
| `OPEN-ROW WHERE <col> = <value>` | Push a PO frame from the single row whose `<col>` equals `<value>` — addresses a fixture by reference, not index. Strict: 0 or >1 matches fail. Value is service-string form (same convention as `SET`); only `=` is supported. |
| `OPEN-ROW Detail "<name>" <index\|WHERE …>` | Select the row from the named detail query on the current PO (`PersistentObject.Queries`) instead of the current Query. The `Detail` clause is orthogonal to the positional/`WHERE` choice. |
| `SELECT-ROWS <ALL\|ALL EXCEPT <i\|WHERE …>\|NONE\|<i>\|WHERE <col> = <value>>` | Set the current query's selection so a selection-gated `ACTION` (e.g. `Delete`) can run. `ALL` is server-side select-all: sets `Query.AllSelected` (serialized as `allSelected`) so the action operates on every matching row on the backend, regardless of what's loaded — `SelectedItems` stays empty. `ALL EXCEPT <index\|WHERE>` is inverse selection: the addressed rows become the server-side exclusion set. `<i>` / `WHERE` (non-strict) / `NONE` set explicit rows and clear the flag. Replaces the selection (never accumulates), never pushes a nav frame; `CanExecute` flips automatically (with `ALL`, the rule sees `TotalItems` minus exclusions). Optional leading `Detail "<name>"` targets a detail query, orthogonal to the target. |
| `DELETE-ROW Detail Attribute "<name>" <i\|WHERE …>` | Remove a row of a detail attribute (`PersistentObjectAttributeAsDetail`, not a detail *query*): marks the row `PersistentObject.IsDeleted` (serialized as `isDeleted`, so the server sees it in `DeletedObjects` on `SAVE`). Gated like the web client's delete button — PO in edit (`guard-edit-mode-required`), attribute not read-only, and unless the PO is new the details query offers a `Delete` action. `WHERE` is strict (unique match). Read rows with `EXPECT Detail Attribute "<name>" TotalItems` / `ROW <i> <col>` (rows = not-deleted; parsed in `Parser.ParseDeleteRow`/`ParseDetailAttributeSubject`, run via `VidyanoSession.DeleteDetailAttributeRow`/`GetDetailAttributeRows`). The `Attribute` keyword only counts after `Detail` when a string literal follows. |
| `ADD-ROW Detail Attribute "<name>" [AS @i]` / `SET Detail Attribute "<name>" ROW <i> <col> = <value>` | Add a row to a detail attribute and fill its cells. `AS @i` binds the new row's index as a variable (`{{i}}`; declared for the lint in `VariableUseAnalyzer`), so `SET … ROW {{i}}` needn't hard-code it. `ADD-ROW` mirrors the web client's add button via the new Core `PersistentObjectAttributeAsDetail.NewObjectAsync` (details query `Query.New`) + `AddObjects`; it needs edit mode, a writable attribute, and a `New` action on the details query. The web client's LookupAttribute picker / OpenAsDialog dialog are not simulated — set cells with `SET … ROW` (every SET value form, same guards, via `VidyanoSession.SetDetailAttributeRowCellAsync`). A dirty row marks its owner dirty (`PersistentObject.IsDirty`, as in the web client). `DELETE-ROW` goes through Core `DeleteObject`, which drops a new row instead of flagging it. |
| `GO-BACK` | Pop the top navigation frame, revealing the one beneath (the browser back button). Refuses when the top is a PO in edit (SAVE or CANCEL first) and when already at the root frame. |
| `FOLLOW <attr> [AS @h]` | Navigate from a reference attribute on the current PO to the PO it points at, pushing a PO frame — the .visc equivalent of the web client's "open" affordance next to a reference field. The attribute must be a reference (`PersistentObjectAttributeWithReference`); FOLLOW honors the same `CanOpen` gate (a non-empty reference the signed-in user may read) and loads the target the same way `OPEN-ROW` loads a query row. It does **not** change the reference — that's `SET`. Composes after `OPEN-ROW` (open an order row, then `FOLLOW Customer`). |
| `FOLLOW-NAVIGATE [AS @h]` | Open the page the **previous verb's** `Navigate(path)` client operation points at (the browser following a server navigate). Reads `LastOperations` (so the interpreter exempts it from the per-verb reset; `VidyanoSession.FollowNavigateAsync` resets the buffers itself after reading) — none → `state-no-navigate`, several → `resolve-navigate`. The path resolves through `RouteTable` (`Runtime/RouteTable.cs`), a port of the web client's `application.ts #setRoutes` + `app.ts _convertPath` over the Application's `Routes` attribute (parsed once per Application): route names raw or kebab-cased (`RouteTable.ToKebabCase` mirrors `String.toKebabCase` char-for-char), optional program-unit prefix, everything after a PO route's first `/` is the object id (ids with `/` survive), plus the raw `[pu/]persistent-object.<id>[/<oid>]` / `[pu/]query.<id>` routes. Opens via `OpenPersistentObjectAsync` / `OpenQueryAsync` (no parent). Unmatched path → `resolve-navigate` with a route-name suggestion. |
| `SEARCH <text>` / `SEARCH Detail "<name>" [text]` | Text-search the current Query in place (no stack change). An optional leading `Detail "<name>"` retargets a named detail query on the current PO — searching it in place (no nav frame, no selection change) to **load** its rows so a following `EXPECT Detail … TotalItems` sees server-created state; omit the text to load with an empty filter. A bare identifier `Detail` is the keyword; quote it (`SEARCH "Detail"`) to search the current query for the literal word. A search the server **rejects** (Core's `Query.SearchAsync` catches the failed ExecuteQuery and sets it as the query's Error notification) fails the verb with `assert-notification-error` + the message, mirroring a failed query `ACTION`; `VidyanoSession.SearchAsync` clears the target's notification first (Core's search never clears it on success, the web client's `setResult` does), so a stale error from an earlier verb neither fails the search nor lingers. A trailing `EXPECTING ERROR` asserts the rejection (see the EXPECTING ERROR row); in the no-text `SEARCH Detail "<name>" EXPECTING ERROR` form, `EXPECTING` is the suffix, not the text. |
| `EDIT` / `CANCEL` / `SAVE` | Standard PO edit lifecycle. SAVE pops + lets owner-driven refresh fire. |
| `SET <attr> = <value>` | Change an attribute; reference SET resolves through lookup. `SET <attr> = ID "<key>"` / `LOOKUP "<display>"` resolve a reference/option; `SET <attr> = null` clears it. |
| `SET <attr> = FILE "<path>"` | Attach a file to a `BinaryFile`/`Image` attribute. The interpreter reads the file (path-security + I/O) and the session formats it for the attribute's data type — `BinaryFile` → `"<filename>\|<base64>"` (via the new `Vidyano.BinaryFile` Core type), `Image` → bare base64; any other type fails loudly (`parse-unexpected-token`). The path resolves against the **FILE root** — `VidyanoScriptOptions.FileRoot` / CLI `--file-root`, defaulting to the running script's directory — and is **confined** to it via the ported `SafePath.TryResolveContained` (`..` traversal, absolute, and drive-qualified paths → `resolve-file`). FILE never combines with `ID`/`LOOKUP` (one RHS keyword). |
| `SET <attr> LANGUAGE <lang> = <value>` | Set ONE translation of a `TranslatedString` attribute (`DataTypes.TranslatedString`). A `TranslatedString` carries a per-language map `{"en":…,"nl":…}`; the **supported languages are server-decided per attribute** (carried in the attribute options — `Options[0]` full JSON map, `Options[1]` current language, `Options[2]` language display names), so Core never holds a global language list. A bare `SET <attr> = <value>` writes the session's **current** language (`Options[1]`); the `LANGUAGE <lang>` clause (a value expression, like SIGN-IN's) names a specific one. The session routes both through the new `PersistentObjectAttribute.SetTranslationAsync` / `SetCurrentTranslationAsync` helpers, which write the per-language map into `Options[0]` (the channel the **server reads back on save** — not `Value`, see `PersistentObjectActions2`) and mirror the current-language string into `Value` for display + dirty tracking. Read with the explicit cast `(Vidyano.TranslatedString)attr`. `LANGUAGE` only applies to a TranslatedString attribute and can't combine with `LOOKUP`/`ID`/`FILE` (parser-gated). Languages from `--var`-style interpolation work (`SET Title LANGUAGE {{lang}} = …`). |
| `ACTION <action>` | Invoke an action by name. Optional leading `Detail "<name>"` targets a detail query on the current PO (`PersistentObject.Queries`) instead of the nav-stack query — the action resolves from and executes against that detail query (parent stays the master PO), so a `SELECT-ROWS Detail "<name>"` selection has a verb to act on. A query action with **no selection** posts an empty `selectedItems` array (not null — `Client.ExecuteActionAsync` coerces it, mirroring the web client), so a server action that only calls `EnsureQuery()` is drivable without a meaningless `SELECT-ROWS`. A query action that **errors** server-side sets the error on the **Query** (no PO); `ExecuteActionAsync` now fails on `(detailQuery ?? CurrentQuery)`'s error notification too (`assert-notification-error`), not just `CurrentPo`'s — so a failed query action no longer passes silently. A custom action can also signal its outcome by **returning** a `Vidyano.Notification` PO (`return Notification(message, type)`) instead of setting it on the parent and returning null; Core's raw `ExecuteActionAsync` hands that PO back untouched, so `VidyanoSession` mirrors the web client (`action.ts _onExecute`): it copies the message onto the frame the action ran against (the query for a query action, else `CurrentPo`) so `EXPECT Notification` can read it, never pushes it as a frame, and fails the op (`assert-notification-error`) **only** when `NotificationType.Error` — an info/warning notification surfaces but passes. When the server result is a **`Vidyano.AddReference`** wrapper PO (a custom action that returns `AddReference("<query>")`), the action does NOT push a PO frame — it reparents the wrapper's picker query to the action's parent (`CurrentPo`, via the now-public `Query.Parent` setter, mirroring the web client's `query.parent = this.parent`) and pushes an `AddReferenceEntry` modal frame; confirm it with `ADD-REFERENCE`. When the server result is a **`Vidyano.RegisteredStream`** (a custom action that returns `Manager.Current.RegisterStream(...)`), the action does NOT push a frame — it **auto-fetches** the stream via `Client.GetStreamAsync` (mirroring the web client's `ActionBase`), buffers `(name, bytes)` in `LastStream` (a `CapturedStream` record) for `EXPECT Stream.*`, and clears it on the next verb (`ResetLastStream()`, alongside `ResetLastOperations()`). A fetch fault (non-2xx `GetStream`) lands as a notification on the frame the action ran against (query action → the query, else `CurrentPo`) and fails the verb (`assert-notification-error`), so `ACTION … EXPECTING ERROR` pins it; a server `OnGetStream` fault served as the response *body* arrives as bytes and is read via `EXPECT Stream.Text`. The stream is fetched **once** on every form: on the `= "option"` path Core's `ActionBase.Execute` already fetches it and hands it to `Hooks.OnStream`, which `ScriptHooks` forwards into `LastStream` (`StreamObserver`), so the session does not re-fetch (a fetch fault there is read off the notification `ActionBase` set). The built-in **exports** (`ACTION ExportToExcel` / `ACTION ExportToCsv`, a `QueryAction` by name) never post `ExecuteAction` — mirroring the web client (`actions.ts` `ExportToExcel`/`ExportToCsv` → `service.getStream`), they post one action-form `GetStream` via the Core overload `Client.GetStreamAsync(action, parent, query, selectedItems, parameters)` with the action's own `Parent`/`Query` and **no selection** (the web client exports the whole query). Core's `ExportToExcel`/`ExportToCsv` action classes do that inside `Execute(option)` (handing the file to `Hooks.OnStream` → `ScriptHooks.StreamObserver` → `LastStream`), so an `= "option"` just runs `Execute`; `Execute` takes no named parameters, so the bare/`(params)` forms post the same `GetStream` from the session; the file lands in `LastStream` through the same `CaptureStreamAsync` as a RegisteredStream (per-verb clear, non-2xx → notification + `assert-notification-error`; a server failure is an `Error.txt` body). |
| `CHART "<name>" [Detail "<name>"]` | Run a named query chart via the `QueryFilter.Chart` system action (the same call the web client's dashboard makes) and **capture** the returned chart JSON for `EXPECT Chart` / `EXPECT Chart.Data`. Unlike `ACTION`, a chart is a read-only observable of the query, **not** a nav destination: `VidyanoSession.ExecuteChartAsync` posts `Client.ExecuteActionAsync("QueryFilter.Chart", query.Parent, query, null, {name})` (parent is the query's own `Parent`, faithful to `QueryFilter.SemanticZoom` — not `CurrentPo`), reads the returned hidden Chart PO's single `Data` attribute (the aggregated chart JSON) into `LastChart` (a `CapturedChart` record), and pushes **no** frame, so `CurrentQuery` is unchanged. The capture is cleared by the interpreter's per-verb reset (`ResetLastChart()`, alongside `ResetLastOperations()`), so `EXPECT Chart` reads only the immediately preceding verb's chart. Optional leading `Detail "<name>"` runs the chart against a detail query (resolved via `ResolveRowQuery`, like the row verbs). A missing chart name comes back as an `Error` notification (`Missing chart <name>`) on the returned PO, which fails the verb (`assert-notification-error`). The chart name is a value expression, so `CHART "{{name}}"` interpolates; a bare identifier (`CHART SessionsHistory`) also parses. No `EXPECTING ERROR` suffix (first cut). |
| `SAVE EXPECTING ERROR` / `ACTION <action> EXPECTING ERROR` / `CONFIRM <option> EXPECTING ERROR` / `SEARCH … EXPECTING ERROR` / `OPEN PersistentObject\|Query\|MenuItem … EXPECTING ERROR` / `OPEN-ROW … EXPECTING ERROR` | Trailing suffix on the fallible verbs that asserts the **negative path**: the verb passes iff it fails as expected, and **fails if it unexpectedly succeeds** (`assert-expected-error`). For `SAVE`/`ACTION`/`CONFIRM`/`SEARCH` the expected failure is a server error notification (`assert-notification-error`; for `SEARCH`, a rejected search — every form incl. `Detail "<name>"` — whose error stays on the searched query for `EXPECT Notification`) — whether the server set it on the PO/query and returned null, or the action *returned* it as a `Notification(…, Error)` result; only that notification is absorbed — a client-side guard (e.g. `guard-edit-mode-required` from SAVE before EDIT, or `guard-action-not-available`) or transport fault still fails. **`CONFIRM … EXPECTING ERROR`** rides the same `WrapExpectingError` inversion on the resumed action's `OpResult` returned by `ConfirmRetryAsync` (default kind `AssertNotificationError`): it passes iff answering a retry dialog resumes an action that then fails (the archetypal "Cancel" branch that throws / returns an error server-side), and fails if the resume succeeds — or parks a *further* retry (which returns `Success`, so the author should `CONFIRM` again). The error notification stays on the current PO (or, for a query action, on the current Query), so a following `EXPECT Notification …` / `EXPECT Notification.Type = "Error"` pins the message. Composes with every ACTION form (`= option`, `(params)`, `Detail "<name>"`) and with `SAVE @initial`. All three **`OPEN`** forms take the suffix to assert the open is **refused**, each accepting a per-form error-kind set (the shared inversion is `WrapExpectingError(stmt, res, params kinds…)`; `params`-empty defaults to SAVE/ACTION's `AssertNotificationError`): `OPEN PersistentObject` → `{server-error}` (`DoOpenPo`); `OPEN Query` → `{resolve-query, server-error}` (`DoOpenQuery`); `OPEN MenuItem` → `{resolve-menu-item, resolve-query, server-error}` (`DoOpenMenu`, since a resolved leaf delegates to the PO/Query load); `OPEN-ROW` (every form) → `{server-error}` (`DoOpenRow`), absorbing a row whose PO **load** is refused server-side while a client-side selection failure (`assert-failed`: out-of-range index / no or ambiguous WHERE match) stays loud. A client-side authoring guard (e.g. OPEN before SIGN-IN, `state-not-signed-in`) is **never** in the set, so it still fails. A refused **`OPEN`** (all three forms, plus `FOLLOW` / `FOLLOW-NAVIGATE`) pushes **no frame**, but `VidyanoSession.RefusedOpen` keeps the exception message as `LastOpenRefusal` (a per-verb observable, cleared by `ResetVerbObservables` before the next executable verb), and `EXPECT Notification` / `Notification.Type` read it first (type `Error`) — so the refusal is assertable even with an older frame on top. Caveat: a refused open is **indistinguishable from a transport fault** (Core's `PostAsync` collapses every open failure into one error channel) — pin the message. `OPEN-ROW` differs: a refused row-open pushes no PO frame but `QueryResultItem.Load` sets the error on the **still-current calling query** (mirroring the web client), where `EXPECT Notification` reads it. Not yet mirrored: the web client also refuses a `GetPersistentObject` that *returns* a PO with an `Error` notification; Core/visc open it as a frame. |
| `CONFIRM "<label>"` / `CONFIRM ID <index>` | Answer a **server retry dialog**. When an action handler calls `Manager.Current.RetryAction(title, message, options, …)` mid-`ExecuteAction` (the web client's `onRetryAction`), Core's retry loop pauses the verb and `.visc` surfaces it as a modal nav frame — `EXPECT NavStack.Top.Kind = "RetryDialog"`, read via `EXPECT RetryDialog.Title` / `.Message` / `.Options`. While it's open the script is **frozen** to `CONFIRM` / `SET` / `EXPECT` (anything else trips `state-retry-pending`), mirroring the `@initial` gate. `CONFIRM` picks one of the offered options by label or by `ID <index>` and **resumes the action** (the ACTION/SAVE runs as a parked coroutine, ping-ponging with the interpreter via two `TaskCompletionSource`s); on a further server retry it re-parks as a new dialog. If the retry carried a PersistentObject for extra input, `SET` its attributes first — `CurrentPo` is the retry PO while the dialog is open, so the edits ride back via `retryPersistentObject`. No dialog open → `state-no-retry-pending`. A trailing `EXPECTING ERROR` asserts the resumed action **fails** (see the EXPECTING ERROR row). |
| `ADD-REFERENCE` / `ADD-REFERENCE <i>` / `ADD-REFERENCE WHERE <col> = <value>` | Confirm an **Add-Reference picker** opened by an `ACTION` whose server result was a `Vidyano.AddReference` (an `AddReferenceEntry` modal frame, `Kind = "AddReferenceDialog"`). Posts the faithful `Query.AddReference` call — the web client's `executeAction("Query.AddReference", parent, picker, selectedItems, {AddAction}, skipHooks)` — with the entry's `Parent`, picker, chosen rows, and the originating action's name as the `AddAction` parameter (so the server routes to the right `OnAddReference`). The picker is the `CurrentQuery` while open, so `SEARCH` / `SELECT-ROWS` / `EXPECT TotalItems` drive and inspect it. The bare form confirms the picker's current selection (from a prior `SELECT-ROWS`); the inline `<i>` / `WHERE` selector (reuses `ParseRowTarget`, no `Detail` clause) selects on the picker first, then confirms. While the picker is open the script is **frozen** to `ADD-REFERENCE` / `SEARCH` / `SELECT-ROWS` / `EXPECT` / `REQUIRES` / `GO-BACK` (anything else → `state-add-reference-pending`). Confirming with no selection → `assert-failed`; no picker open → `state-no-add-reference-pending`. On success the picker frame pops; a server-side failure leaves it open and surfaces as `assert-notification-error`. A query's **built-in** `AddReference` action (a detail query's Add button, offered when the query has a `LookupSource`) also opens a picker: `ExecuteActionAsync` intercepts a `QueryAction` named `AddReference` (bare, or the last — "Existing" — option of Core's merged `AddAndNewAction`) and, mirroring the web client's `app-service-hooks-base.onAction`, posts nothing — it pushes an `AddReferenceEntry` whose picker is `Query.Clone(asLookup: true)` (new public Core API) of the action's query, with `SourceQuery` set; the confirm then posts `Query.AddReference` against `SourceQuery` with the action's own parameters and **no** `AddAction` (`executeServiceRequest()`). No query refresh follows (`SEARCH Detail` to reload, as for custom pickers). **Removing** a reference has no verb — select the linked rows and run the server's remove action: `SELECT-ROWS Detail "<name>" WHERE …` then `ACTION Detail "<name>" Remove`. |
| `EXPECT <state>` | Assert on `NavStack.*`, `TotalItems`, `Selection.Count`, `Selection.AllSelected`, `IsInEdit`, `ClientOperation <type>`, `RetryDialog.Title`/`.Message`/`.Options` (the open server retry; null when none), `Stream`/`Stream.Name`/`Stream.Length`/`Stream.Text` (the stream the previous action auto-fetched or exported — `LastStream`; bare `Stream` reads naturally with `IS NULL`), `Chart`/`Chart.Data` (the last `CHART`'s JSON, or null; both spellings resolve to `LastChart?.Data`, so bare `Chart` reads naturally with `IS NULL`), attributes, notifications. `EXPECT <ref> = ID "<id>"` (and `!= ID`) asserts a **reference attribute by its document id** (`PersistentObjectAttributeWithReference.ObjectId`), symmetric with `SET <ref> = ID`; the hint rides on the `ExpectSubject` so `REQUIRES` inherits it. Only `=`/`!=` and only `Attribute`-kind subjects accept `ID` (parser-gated); `= ID` on a non-reference attribute fails loudly rather than silently comparing the display value. `EXPECT <attr> LANGUAGE <lang> = "..."` asserts ONE translation of a `TranslatedString` attribute (reads `((TranslatedString)attr)[lang]`), symmetric with `SET <attr> LANGUAGE`; a bare `EXPECT <attr> = "..."` compares the current-language `Value`. `LANGUAGE` rides on the `ExpectSubject` (so `REQUIRES` inherits it), is only valid on an `Attribute` subject of type TranslatedString, and can't combine with `= ID` (parser-gated). `Notification` / `Notification.Type` read the current PO's notification, or the current **Query**'s when no PO is open (`po is not null ? po… : query…`) — so a query action's notification is assertable. `Selection.AllSelected` is the server-side select-all flag (`Query.AllSelected`); `Selection.Count` stays literal (0 for pure all, the exclusion count for inverse). Metadata forms: `Attribute X TYPE/TAG/TYPEHINT <k>`, `PO.<prop>` / `PO.Metadata.<k>` / `PO.NavigationHints.<k>`, `Query.<prop>` / `Query.Metadata.<k>` / `Query.NavigationHints.<k>` / `Query.PersistentObject.<prop>` / `Query.Columns[<name>].<prop>`. `Selection.Count` / `Selection.AllSelected` (and `TotalItems` / `Query.*`) are `Detail "<name>"`-redirectable. `EXPECT Action <X> IS [NOT] AVAILABLE | VISIBLE` asserts a named action's gating on the current PO / nav-stack query; a leading `Detail "<name>"` redirects it to a detail query's action — resolved against that detail's `Actions`/`PinnedActions` **alone**, never the master PO (which may carry a same-named action), symmetric with `ACTION Detail "<name>" <X>`. Only AVAILABLE/VISIBLE compose with `Detail` (DISPLAY-NAME does not). `EXPECT Attribute <X> IS [NOT] PRESENT` (`AttributeFlagKind.Present`, scoped `@session.X` too) and the **leafless** `EXPECT Query.Columns[<X>] IS [NOT] PRESENT` (`QueryColumn` with `MetadataKey` null; Detail-redirectable) assert existence in `PO.Attributes` / the query's columns, independent of visibility — the one assertion a missing name (server `RemoveAttribute` / `RemoveColumns`) satisfies; every other EXPECT on it still fails `resolve-attribute`. The parser only lets a leafless column take `IS [NOT] PRESENT`. |
| `TOOL <name> [k=v, …] [-> @var]` | Call a registered C# delegate. Named args only; throws become `tool-error` diagnostics. In-process: register on `VidyanoScriptOptions.Tools`. From the CLI: implement `IVidyanoScriptToolPack` in a DLL and pass `--tools <path.dll>`. |
| `EXPECT Detail "<name>" <query-subject>` | Target a detail query on the current PO for query-family subjects (`TotalItems` / `Query.*`). Reads what the detail Query holds in memory (no forced search) — a detail is lazy, so load it first with `SEARCH Detail "<name>"` if it hasn't been opened (e.g. to see rows a SAVE created server-side). The same `Detail "<name>"` clause also targets a named **action** on that detail for gating: `EXPECT Detail "<name>" Action <X> IS [NOT] AVAILABLE | VISIBLE` (resolved against the detail's `Actions`/`PinnedActions` alone). |
| `EXPECT <lhs> MATCHES "<regex>"` | Regex assertion on the subject's string form (1s ReDoS-guard timeout; null never matches). |
| `REQUIRES <expect-subject> <op> <value>` | Precondition gate reusing the full EXPECT grammar. Holds → pass + continue. Unmet/unevaluable → skip the rest of the body (`state-requires-unmet`, not a failure). |
| `REQUIRES TOOL <name>` | Capability gate; skips the body unless a tool of that name is registered. |
| `CLEANUP` | Marker; statements after it always run, even when the body was skipped by an unmet `REQUIRES`. |
| `REPEAT <n> [AS @i]` … `END` | Run the `END`-terminated block `<n>` times — bounded iteration that stays **total** (the bound is fixed at entry; no body can extend it). `<n>` is a literal/interpolation resolving once to a non-negative int (negative/non-int → `state-invalid-bound`; `REPEAT 0` runs zero times). `AS @i` binds the zero-based iteration index as a loop-scoped variable, **read in the body as `{{i}}`** (no `@` — user vars are assigned `@name`, read `{{name}}`); a prior binding of that name is saved and restored. Each iteration restores the nav stack to its entry depth (loud-fail `state-loop-edit-left-open` if a PO is left in edit). Nests arbitrarily; `REQUIRES`/`CLEANUP`/`###` inside a block is a parse error. |
| `FOR-EACH ROW [Detail "<name>"] [WHERE <col> = <value>] [AS @row]` … `END` | Iterate the **currently-loaded** rows of the current query (or a named detail), optionally filtered by an equality `WHERE` (non-strict; 0 matches → body runs zero times). The matching set is **snapshotted at entry by row identity**, so body mutations (e.g. `Delete`) can't shift the iteration. No positional-index form — `WHERE` is the only filter. `AS @row` binds a loop-scoped row handle: read a cell with `@row.<col>` / `{{@row.<col>}}` (service-string form), push its PO with `OPEN-ROW @row` (opens by snapshotted identity, not a live index); the row is also mirrored into the variable table, so a `TOOL` in the body reads the whole `QueryResultItem` as `ctx.Variables["row"]`. If the server holds more rows than were loaded, a warning names the gap (no silent truncation). Each iteration restores the nav stack to its entry depth (same edit guard as `REPEAT`/`GO-BACK`). |
| `@expects <a>, <b>` | Declare variables the **host** supplies at run time (`VidyanoScriptOptions.Variables` / `--var` / `--env-prefix`) so a `{{a}}` read doesn't false-positive in the lint. An `@`-directive (like `@mode`/`@app`), **not** a verb — so it needs no `VerbCatalog`/`KeywordCatalog` entry. Pure no-op at run time: it never writes the variable table, so the host value stays required and is never overwritten (unlike the `@a = "{{a}}"` self-assign hack). An unsupplied declared var still loud-fails (`resolve-variable`) at first read; the lint is presence-only so placement is free (conventionally top-of-file). Names are bare, comma-separated. Parsed in `Parser.ParseExpectsDirective`; AST `ExpectsDirective`; analyzer counts the names in `VariableUseAnalyzer.CollectDeclarations`. |
| Built-in vars `{{@today}} {{@now}} {{@uuid}} {{@random}}` | Evaluated on each reference (like `DateTime.Now` / `rng.Next()` in C#) — capture into a var to freeze (`@id = {{@uuid}}`). `--seed <int>` / `.Seed` fixes the `@uuid`/`@random` sequence (independent streams, next value per reference); `--now <iso>` / `.Now` anchors the clock, which then flows by real elapsed time (so `@now` is anchored but not bit-reproducible). |
| `"... {{x}} ..."` (in-string interpolation) | `{{...}}` holes resolve inside string literals (same forms as a standalone `{{...}}`), so values compose: `SET Name = "Acme {{@uuid}}"`. Escape a literal brace as `\{`. Hole-free strings are unchanged. |
| Current-PO values `{{PO.<prop>}}` / `{{PO.Attr.<name>}}` | Read the current PersistentObject (top PO frame) in any value position, so a value seen on a record (e.g. `@id = {{PO.ObjectId}}` of a record created at run time) can be reused. `Interpreter.ReadCurrentPoValue` maps the path to the EXPECT subject it names and calls `ResolveExpectSubject`, so the value is exactly what that EXPECT compares: `Attr.<name>` → `Attribute` (same hidden guard), `Metadata.<k>` / `NavigationHints.<k>` → the bag lookups, anything else → `PoProperty` (`ObjectId`, `Type`, `Label`, …). Attributes live under `Attr.` so a `Type`/`Label` attribute never shadows the PO property. No PO frame → `state-no-current-po`. The `PO.` prefix is ordinal (like `Messages.`) and skipped by `VariableUseAnalyzer.IsPlainVariable`. |
| Env values `{{env:NAME}}` / `{{env:NAME ?? "fallback"}}` | Source a value from the environment in any value position. `{{env:NAME}}` is loud-on-missing (`resolve-env`); `?? <fallback>` (quoted string or bare token) supplies a default when unset. `--env-file <path>` loads literal `KEY=VALUE` pairs from a `.env` (full-line `#` comments + optional `export `; no quoting/`${VAR}` expansion) that back `{{env:NAME}}` / `SIGN-IN FROM ENV`, shadowing the process env; repeatable, last wins. `--env-prefix <prefix>` / `.EnvironmentPrefix` bulk-binds matching **process** env vars into the variable table with the prefix stripped (`VIDYANO_REGION` → `{{REGION}}`; not fed by `--env-file`); an explicit `--var` / `.Variables` binding wins. Hosts inject `.EnvLookup` for hermetic test runs (the seam `--env-file` composes). |

### Maintenance notes
- The script projects pin to `Vidyano.Core` via `ProjectReference`, not `PackageReference` — they always build against the same-tree Core. After cutting a Core release, bump the script projects' versions in lockstep.
- `ScriptHooks.OnClientOperation` and `ScriptHooks.OnRetryAction` override Core `Hooks` virtuals living on `Hooks.cs` in Vidyano.Core. Changes to either signature need a coordinated update in `ScriptHooks.cs`. `OnRetryAction` returns the chosen option string Core posts back as `RetryActionOption` (the web client posts `options[idx] || idx`); the `VidyanoSession` retry coroutine drives it and serializes any `SET`s on the retry PO through Core's `data["retryPersistentObject"]`.
- Round-trip metadata: `PersistentObject`/`Query`/`PersistentObjectAttribute` `GetServiceProperties` include `metadata`/`tag`/`navigationHints` so server-side action handlers see the same shape a browser would post. Don't strip these.
- `PackageReadmeFile` and `PackageIcon` are wired for all three packages — each project's `README.md` (the root `README.md` for Core) and the shared `Vidyano.png` ship inside the nupkg. These READMEs are slim pointers into `docs/` (see **Documentation** above); keep their doc links absolute so they render on nuget.org.
- **Docs are canonical.** When you add or change a `.visc` verb, CLI flag, or other user-facing behavior, update the relevant `docs/` page (`visc-language.md` / `cli.md` / `embedding.md` / `core.md`), the `.visc` quick-reference table above, and `vidyano help verbs` (`Diagnostics/VerbCatalog.cs`) together. The `KnownVerbs ⊆ VerbCatalog.Names` guard test catches a missing catalog entry; nothing automatically catches stale docs, so treat it as part of the change.
